# iPad 持续补帧掉帧排查

用户环境：M5 iPad Pro，RIFE Lite + 默认画质，1080p / 23.976 fps SDR 网络视频。用户反馈连续播放约八分钟后掉帧，没有主动使用倍速或拖动。此次诊断与前一轮短时/本地夹具验证分别记录，不能用旧测试代替本次真实播放。

## 真实播放记录（修改前）

在用户确认开始卡顿时保存只读性能记录。网络缓存充足、没有缓冲暂停，VideoToolbox 解码丢帧为零；GPU pass 平均合计约 1.8–4.3 ms。系统温控从 nominal 进入 fair，之后进入 serious，但 nominal 阶段已出现渲染丢帧。因此不能把问题仅归因于过热，也未测量实际 CPU/GPU 频率来证明降频。

RIFE 完整处理区间包含硬件帧下载、float RGB 转换、模型推理和输出复制。平均约 37–39 ms，接近每个原始帧约 41.7 ms 的时间预算；原来的 `inferenceMs` 单项没有包含全部成本。用户报告卡顿时，当前计数段已累计 613 个渲染丢帧，完整处理时间超过源帧间隔的比例约 10%。后期较高温控阶段此比例进一步上升。记录中有两次进度跳变，统计按连续片段处理，不把跨跳转的计数器直接相减。

原生滤镜同步运行在 mpv 播放/控制线程上。一次昂贵的转换和推理会阻塞及时送帧及属性读取；平均吞吐接近实时并不保证每个补帧后的显示时限都能满足。

## 调度改动

保留原来的模型、像素处理、时间戳、倍速旁路和默认 shader。`vf_tigerest_rife_async.c` 使用固定版本 mpv 的私有滤镜图和异步队列，让整个原滤镜在工作线程运行，播放器线程仅传递帧和读取已缓存的诊断快照。

- 输入队列最多 2 帧 / 64 MiB，输出队列最多 4 帧 / 128 MiB，提供有上限的预缓冲。
- 输出达到帧数或字节任一上限后开始发送；短视频遇到输入 EOF 也能排空。复核发现只等四帧会让大尺寸原帧受字节上限阻塞，已新增失败回归并修正。
- 拖动时清空两侧队列并同步重置工作图，防止旧帧混入新位置。销毁时先停止并等待工作线程退出，再释放滤镜和队列。
- 诊断计时只在显式准备的探针中编译。正常工程和应用不包含播放追踪入口。

队列不能永久弥补推理平均速度慢于片源的情况；本次没有以自动降低画质或关闭补帧掩盖处理不足。

## 真实播放复测反馈

用户随后确认异步版本仍会掉帧，期间一直正常播放，没有倍速或拖动。此前的本地夹具通过不能作为问题已解决的依据。普通应用未开启性能记录，不能把旧记录当作这一轮数据。Xcode beta 的 LLDB 在附加运行进程时崩溃，未取得有效快照；已向应用发送继续运行指令。

继续使用同一调度版本收集真实播放证据，探针增加有界队列占用、弹幕绘制耗时/回调间隔、实际同步选项和主线程采样间隔。只记录数字与固定枚举，不记录弹幕文本或媒体地址；这些字段只存在于显式诊断构建。

## 异步版本真实片源复现

在用户开始同一片源后实际抓到持续掉帧。初期输出队列有 2–4 帧余量，转换约 8–9 ms；随后转换升到约 12–15 ms，整帧处理约 42 ms，输入队列长期满（2 帧）、输出队列经常为零。最新归档含 378 个 active 样本，渲染丢帧计数达到 4798；nominal 温控阶段已经累计 168 帧，随后 fair / serious 阶段继续增加。网络缓存充足、未缓冲、解码丢帧为零。弹幕回调约 120 Hz，通常每两秒绘制总耗时约 5–11 ms，没有发现与掉帧同步的主线程阻塞。

结论限于：异步队列解决控制线程阻塞，但在真实环境中仍缺乏稳定的处理余量。不能仅归因于温控，也不能用本地夹具结果宣告修复。尚需区分硬件帧下载、颜色转换及 CPU 调度等待的贡献。

准备仅限探针的分段 wall/CPU 计时和 QoS 对照：同一播放内 default→user-initiated→default→user-initiated，最终回到 default，不改变画质或播放偏好。真实 MPVKit 队列测试先因未支持指令而失败，加入诊断指令后 worker 线程 QoS 往返与非法参数拒绝通过；正常构建不包含该指令。对照诊断应用已安装，等待用户重新开始视频；尚无对照结果，未增加新的生产修复。

## QoS 对照结果及转换优化候选

上述真实片源对照已完成并归档。实际 worker QoS 确认 21→25→21→25→21，系统调用无错误；在累计 480 秒活动播放后自动恢复 default。排除各阶段前五秒后，四段转换时间中位数分别为 11.45、13.27、13.22、12.85 ms，整帧处理约 40.46、41.90、41.86、41.64 ms，所有阶段仍有渲染丢帧。温控随时间变化，不能据此声称高优先级使掉帧更严重；可以确认提高优先级并未解决此问题，不将该设置带入正常版本。

拆分计时显示硬件帧下载约 0.1 ms，颜色转换约 13 ms；转换线程 CPU 时间与墙钟时间基本一致，主要是实际计算而非等待。真实解码格式为 NV12。新候选将 8 位 BT.709 NV12→GBRPF32 的双线性色度采样与矩阵转换交给 Metal，保留现有 RIFE 模型、默认 shader、输出精度和时序。共享输入/输出缓冲固定复用；其他格式、矩阵、范围、色度位置或 Metal 失败仍在同一帧回退到 swscale，失败后不逐帧重试 GPU 初始化。

Mac 上的合成像素对照覆盖 full/limited、left/center、随机像素/渐变、紧密/带 padding 的 stride 和完整 1080p。初版与固定版本 swscale 最大差异为 0.003904；继续用中性灰阶核对，发现来自旧路径 8→16 位再除以 65535 的归一化。Metal 在裁切前保留同样的 256/257 增益后，17 组最大差异降至 0.00005990，测试阈值收紧到 1/4096。该处理与 [FFmpeg 的 GBRPF32 输出归一化](https://github.com/FFmpeg/FFmpeg/blob/master/libswscale/output.c) 一致；剩余差异为系数量化/舍入，不能声称逐位相等。ASan/UBSan 下像素和边界验证通过。19 项原核心调度测试通过，新增 Metal 选择、初始化/执行失败回退、未知色度位置的 full→center / limited→left 规则；对应回归先失败再修复。以上仍不是 iPad 持续播放性能证据，真机验证待完成。

## Metal 真机夹具验证

Metal 候选真机本地夹具已完成 794.6 秒 / 760 个样本，含正常速度、倍速、五次长按、拖动与 600 样本连续播放段。持续段渲染/解码丢帧均为零，Metal 后端始终生效，转换中位 1.594 ms（p95 3.736 ms），整帧处理中位 27.028 ms（p95 36.445 ms），最大绝对音画偏差 21.347 ms。内存 1214.4–1218.1 MiB，全部持续段温控为 fair。首次进入 1.25× 出现 3 帧瞬时渲染丢帧；后续恢复、长按、拖动未持续增长。持续段有两次采样落在 warming，滤镜统计亦记录若干相邻帧缓存重置，不能把全部样本描述成 active。

同一夹具上一轮 swscale 转换中位 10.57 ms、整帧处理中位 38.009 ms；本轮明显缩短处理时间，但并非严格同初始温控实验。核对合成文件的包时间戳，36、60、84 秒等位置存在约 83.3 ms 的源时间戳间隔，与缓存重置吻合，不是推理失败。该夹具本身的时间戳边界也是验证限制。长测使用归一化微调前的同一 Metal 管线；最终颜色归一化调整另做像素对照、构建和真机 10 样本短测，Metal 生效、渲染/解码零丢帧。随后完成下述最终版本真实片源验证。

## Metal 最终版本真实片源验证

用户再次开始原问题片源，保持 RIFE Lite + 默认画质。归档记录 327 个两秒样本，累计活动播放 657.3 秒（约 11 分钟），视频持续从约 3 分钟续播到 14 分钟，没有暂停、倍速、拖动或缓存暂停。VideoToolbox 解码、三个默认 shader 和弹幕保持开启，源帧率 23.976，补帧输出约 47.952。

- 全部记录的渲染/解码丢帧均为零，推理失败为零。排除开始十秒后，322 个样本全部 Metal / active，重置计数保持 185（初始续播时形成），新增 15,518 个中间帧，输出队列采样最少仍有一帧。
- 颜色转换中位 2.407 ms、p95 4.494 ms；整帧处理中位 29.888 ms、p95 35.135 ms。第八分钟后仍零丢帧，该后段转换中位 1.976 ms、整帧中位 28.499 ms，没有再次变成约 42 ms 的持续处理不足。
- 温控为 106 个 nominal、216 个 fair 样本，没有进入 serious；未测量实际硬件频率，不将此结果解释为已证明发生或消除降频。内存 1323.4–1371.6 MiB，无持续增长。mpv 内部音画偏差字段保持稳定（最大绝对值 0.064 ms），不是外部摄像/音频测量。
- 此结论覆盖当前 M5 iPad、这段真实片源和上述设置。客观计数未复现原有持续掉帧；用户随后明确反馈“目前流畅”，主观观感与本轮记录一致。不据此推断所有内容、任意时长均无卡顿。

诊断记录已归档于本机临时目录。正常 Release 构建签名校验通过，工程与可执行文件排除了诊断入口；普通应用已覆盖安装，保留用户资料与设置。本次未替换公开发布资产。

## 首页修复验证

生产服务器只读核对确认，同一作品有两个不同内部 Series ID，但 `PresentationUniqueKey` 相同。首页改为按类型和该作品标识合并；没有标识时才用内部 ID，不按相似标题合并。保留最新观看记录与续播集、最新入库信息，并在合并后再判断是否已收满 24 部。详情批量请求明确关闭服务器默认分组，以便获得所有别名 ID 的作品标识。JS 和 AppleCore 实现保持相同规则。

真实服务器读取结果从 24 张中的两张重复变为 24 张中的一张，当前 S02E03 续播目标保留。定向首页测试 62 项、AppleCore 全量 103 项、隔离 Chrome 首页交互检查通过；复核发现的原始 ID 数量提前结束翻页问题已有失败回归和修复。误用全目录 Node 测试命令另有三个桌面可执行文件参数缺失的前置失败，不计作产品验证通过。尚未通过此文档宣称该首页修复已安装或公开发布。
