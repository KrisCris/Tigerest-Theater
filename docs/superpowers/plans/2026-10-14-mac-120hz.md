# Mac 120 Hz UI implementation plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task by task.

**Goal:** Make scrolling and transitions approach a stable 120 fps on a supported Mac display, preserving desktop playback and visual behavior.

**Architecture:** Retain the Qt desktop shell initially. Correct cross-world animation coordination, then investigate the Qt WebEngine offscreen compositor's refresh clock before changing the application architecture. A rendering backend change is accepted only when measured.

**Tech stack:** Qt 6.9.3, Chromium 130, Qt Quick, JavaScript, macOS 26+, Xcode 27.

**Spec:** User request in this conversation: Mac transitions and scrolling should target 120 fps.

## Constraints and acceptance

- Preserve installed settings, accounts, mpv playback and desktop features; benchmark with isolated profiles and synthetic content.
- Do not ship unlimited rendering, a hardcoded 120 Hz timer, or private WebKit API switches.
- Distinguish requestAnimationFrame timing, Qt frame submission and actual display presentation.
- Use the same machine, window size, DPR, artwork and GPU setting for comparisons.
- Record median/p95/worst frame interval and missed refresh opportunities. 120 fps has an 8.33 ms budget; an average alone is insufficient.
- Handle 60 Hz displays, screen changes, reduced motion, hidden windows and low power without forcing unnecessary rendering.

## Initial evidence

On this M4 Pro Mac, a simple animated page gives Chrome ~120 rAF/s (p95 9.2 ms), Qt OpenGL ~60 and Qt Metal ~60 (p95 16.8 ms). Qt's unlimited-frame flag produces ~2447 callbacks/s and is rejected. These are scheduling measurements, not proof of physical presentation. An earlier real WebEngine probe also confirmed concurrent page-entrance animation during a shared-element transition because MainWorld globals are invisible to ApplicationWorld.
