# macOS 内置 RIFE 补帧设计

状态：方向已确认，本文待用户审阅。本文是开发设计，不是已实现功能或测试报告。

## 1. 目标与已确认的方向

用户希望在 Tigerest Theater 内直接使用 RIFE 实时补帧，摆脱对外部 SVP 的依赖，并充分利用 M 系列芯片以改善效率。用户已确认：优先验证 Core ML 对 Apple Neural Engine（ANE，即 NPU）的利用，以 Metal 辅助并提供 GPU 备选，依据实际速度、功耗和画质决定默认方案。

交付形态是可直接安装的 Mac 应用：模型、补帧引擎和必要运行时随包提供；一般用户只需要一个补帧开关。模型转换、依赖安装和性能分析属于开发过程，不出现在用户操作流程中。README 只写实际可用的功能与必要限制，开发报告单独保存。

当前只能确认技术接入方向，尚未运行 RIFE/Core ML 基准。本文中的性能数字均为验收要求，不是已有成绩。现有 Mac 包尚未内置 RIFE。

## 2. 本次提议的范围

片源偏好的询问尚未收到单独答复，以下作为本次审阅的明确默认范围：

| 项目 | 第一版行为 |
| --- | --- |
| 平台 | macOS、Apple Silicon；沿用当前工程的最低系统版本 |
| 用户设置 | 视频设置增加「AI 补帧（RIFE）」开关，默认关闭 |
| 倍率 | 2 倍；23.976→47.952、24→48、25→50、29.97→59.94、30→60 fps |
| 片源 | 优先支持恒定帧率、逐行、最高 30 fps 的 SDR 视频 |
| 分辨率 | 1080p 是首个必须通过的实时目标；4K 同时测量，达标的模式才启用 |
| HDR | 第一版保持原帧播放；HDR10、HLG、Dolby Vision 未完成专项验证前不进入补帧链 |
| 性能不足 | 自动恢复原帧播放并说明原因，不靠重复帧显示虚假的补帧成绩 |
| 其他系统 | 现有播放功能继续工作；本期不增加 Windows、Intel Mac 的 RIFE 实现 |

第一版不提供模型下载器、模型选择列表、离线转码或任意目标帧率。HDR 补帧和完整 4K 实时能力不是本设计预先承诺的成果；如果用户要求它们作为首发条件，应在实现前调整范围。

## 3. 技术选择

| 路线 | 作用与取舍 |
| --- | --- |
| Core ML + Metal 辅助（选定） | 优先检验 ANE 执行网络的能力；必要的图像整理、光流变形和合成可使用 Metal。能效目标最贴近用户需求，但模型转换和实际设备分配需要验证。 |
| GPU 执行 RIFE（备选） | 先比较同一个 Core ML 模型的 CPU+GPU 配置，减少第二套模型和推理代码。直接 Metal/MPSGraph 作为后续优化候选，仅在基准证明必要时引入。 |
| ncnn/Vulkan（比较基线） | 可作为相同素材上的性能参照；不是本期面向 ANE 的主引擎，不把它包装成 NPU 实现。 |

Core ML 的 `.all`、`.cpuAndNeuralEngine`、`.cpuAndGPU` 是允许使用的设备集合，不能保证具体算子在哪个设备运行。默认配置必须根据实际执行和端到端数据选择，不能因为名称里含 ANE 就强制使用 CPU+ANE。

模型首先评估官方 Practical-RIFE 4.25 lite；以对应 PyTorch 参考实现校验转换结果。将模型版本、源代码提交、原始权重 SHA-256、转换工具版本和转换参数纳入模型清单。最终包只包含通过验证的模型及必要变体，不在运行时访问模型下载站点。

采用固定尺寸或有限尺寸变体以控制模型编译开销。宽高不足对齐要求时补边，输出按原尺寸裁回，不裁掉视频内容。不同尺寸变体共享原始模型来源；进程只保留一个当前模型实例及其工作缓冲区，同规格定位可复用，规格改变后释放旧实例。应用自有磁盘缓存最多 512 MiB，按最近使用顺序清理；不修改系统管理的 Core ML 缓存。

## 4. 与播放器的接入方式

继续让 mpv 管理解码、音频、时间轴、字幕和最终输出。通过其现有 VapourSynth 滤镜接口接入原生 RIFE 插件，而不是从 Qt 窗口截图再处理。

```text
Emby 播放请求
  → mpv 解码
  → 应用内 VapourSynth 桥接
  → 原生 RIFE 插件：准备两帧 → Core ML 推理 → 合成中间帧
  → mpv 输出原帧与中间帧
  → 现有渲染、字幕和音画同步
```

VapourSynth 和最小 Python 运行时只承担内部滤镜连接；神经网络不使用 Python/PyTorch 做用户端推理。它们随应用提供，用户无需 Homebrew、Python、SVP 或脚本配置。

该接入路径需要可供滤镜读取的帧，第一版使用 mpv 的硬解复制回显模式。它存在帧拷贝开销；基准必须包含这些开销，不能宣称整个链路零拷贝。Core ML 引擎与桥接器分离，以便后续有证据时优化帧传递方式。

## 5. 组件边界

| 组件 | 职责与接口 |
| --- | --- |
| `FrameInterpolationController` | 管理开关、片源资格、开始/停止、错误回退和状态；通过现有 mpv 控制句柄只管理带自身标签的滤镜。 |
| `RifeEngine` | 接收相邻帧、规格和插值位置，返回中间帧及耗时；不读取 Emby 配置、不访问网络、不控制播放器。 |
| Core ML 实现 | Objective-C++ 调用公共 Core ML API，持有模型与复用缓冲区；分别测试允许的计算设备配置。 |
| Metal 辅助实现 | 承担经基准确认需要独立实现的图像变换；与参考模型核对边界、采样坐标和精度。 |
| VapourSynth 插件与薄脚本 | 对接 `video_in`、相邻帧请求、色彩属性和帧时长；调用原生引擎并输出滤镜结果。 |
| 包装与验证工具 | 固定依赖和模型来源，处理相对路径、签名、许可证，并测试无开发环境的安装包。 |

接入文件主要位于 `src/player/`、`resources/settings/settings_description.json`、`resources/mpv/`、`dev/macos/`、`CMakeModules/CompleteBundleMac.cmake.in`、Mac 构建工作流及相关测试。新增推理代码放在独立目录，避免继续把推理、状态和设置逻辑堆入 `PlayerComponent.cpp`。

## 6. 帧、色彩和时间轴规则

第一版每对相邻源帧只计算 `t=0.5` 的中间帧。原帧按原顺序输出，中间帧插入对应时间间隔；用有理数处理帧率与时长，保留 23.976/29.97 的准确时间关系。结尾不得等待不存在的下一帧，最后一段时长必须守恒。

输入为 SDR 时，按已知的矩阵、传递函数、色域、范围和色度位置做模型输入转换；未知色彩信息不能盲目按 HDR 或 BT.709 转换。10 bit SDR 不能为了接口方便强制压成 8 bit。模型内部精度与模型输入输出布局均通过参考测试确定。

场景切换时不在两个镜头之间生成过渡图；由场景判定器选择保留边界画面，保持正确时长，并单独统计跳过次数。字幕、弹幕及播放器 OSD 在补帧之后合成，不送进模型。

实际变帧率、隔行、超过支持帧率或识别出的 HDR 视频跳过补帧。读取初始参数后仍监测运行中的时间戳和格式变化，不能只依赖容器标称帧率。遇到分辨率或色彩格式改变时重新判定资格。

## 7. 生命周期与失败处理

控制器状态为 `Off → Preparing → Active`；不支持的片源进入 `Bypassed`，运行失败或持续超时进入 `DisabledForCurrentItem`。新片开始时允许重新评估，当前片因性能退出后不反复自动开关。

模型准备在工作线程进行。推理使用复用实例与有界请求数，初始只允许一个推理请求在执行、最多两对相邻源帧等待；后续增加并行度必须有收益和内存数据。不得在 Qt 界面线程加载模型或等待推理。

每次换片、定位或停播增加会话代次，过期结果不能进入新时间轴。定位后清空帧依赖，但可保留兼容的模型实例以避免反复加载。VapourSynth 脚本因定位重建时，模型缓存必须按模型、尺寸、精度和计算配置核对，不能共享上一段的图像缓存。

出现模型缺失、插件加载失败、预测异常或不兼容输入时，移除应用自有滤镜并恢复本次临时调整的解码设置，继续普通播放。首批 30 次预测作为预热；随后观察连续两个 3 秒窗口，若不能维持目标吞吐且存在滤镜等待或丢帧，退出当前片的补帧。单次预测失败立即走错误回退；不得把网络缓冲、暂停或拖动进度条算作推理性能不足。可恢复失败必须受测试覆盖。

设置初版在下次打开视频时生效，界面明确提示，避免在播放中切换解码器造成隐式重载。关闭后下一次播放恢复用户原有解码设置；运行时回退只撤销本功能仍拥有的临时值，不覆盖用户随后做出的修改。

## 8. 与已有配置和 SVP 的关系

内置 RIFE 使用应用自有滤镜标签，例如 `tigerest-rife`，不得清空整条用户滤镜链。系统 mpv 配置模式第一版不启用自动接管，开关显示原因并引导使用内置播放配置。

启用内置 RIFE 的会话不建立供 SVP 自动发现的默认 IPC 端点，避免两套补帧同时注入。用户手动配置的 IPC 地址和第三方滤镜不会被偷偷删除；发现外部补帧已在使用时，内置 RIFE 跳过并给出一次简短提示。关闭内置 RIFE 后，已有 SVP 兼容功能仍可按原设置工作。

目前工作区存在尚未完成的 VapourSynth/Python 打包修改；其中独立运行测试尚未通过。实现阶段只复用经过验证的公共打包部分，不能把这些改动当作已完成基线，也不先发布中间 SVP 包。

## 9. 用户界面和状态

视频设置只展示「AI 补帧（RIFE）」及简短帮助：「将支持的视频补至两倍帧率，性能不足时恢复原帧播放。重新打开视频后生效。」

播放诊断页区分设置值和实际状态，例如「补帧中：24→48 fps」「当前 HDR 视频保持原帧播放」「性能不足，已恢复原帧播放」。自动回退只提示一次，不持续弹窗。

计算设备、模型版本、推理耗时和跳过帧数保留在开发诊断中。只有取得运行期 ANE 证据后，才能在对应结果中注明 ANE 已使用；没有证据时写 Core ML，不能依据配置值显示“NPU 加速成功”。

## 10. 验证要求与决策门槛

### A. 模型正确性

固定测试集包含真实运动、动画线条、暗部、细节和镜头切换。使用同一权重和插值位置，与 PyTorch 参考结果对照，检测 NaN/Inf、边缘偏移和补边错误。建议转换正确性门槛为归一化 RGB 下逐样本 PSNR 至少 40 dB、平均绝对误差不高于 0.005；如果某模型需要放宽，必须先说明原因并审阅对应图像，不能仅为让测试通过而改阈值。

参考一致性只用于验证实现，没有证明 RIFE 对真实画面一定没有伪影；还需人工检查遮挡边缘、快速运动、字幕叠加和切镜。

### B. ANE 与性能

在当前 M4 Pro 上比较相同模型的 `.all`、CPU+ANE、CPU+GPU，记录冷加载、预热后的 p50/p95 耗时、内存、实际源帧/生成帧吞吐和执行设备。计算计划用于解释可能的分配；通过 Instruments/Core ML 分析取得运行证据，不能把计划等同于实际执行。

1080p、30→60 fps 是首个集成门槛：预热后每对源帧的处理 p95 目标不超过 26.7 ms，为每对 33.3 ms 的实时预算保留约 20% 余量。还必须在实际播放器中持续播放 10 分钟，排除初始化和用户操作后丢帧比例低于 0.1%；使用带同步闪光与音频脉冲的素材，稳态音画偏差不超过 40 ms，且不随播放时长增长。单独模型达到指标而完整播放失败，仍判定未达标。

4K 同时测完整推理和保持输出原尺寸的低分辨率光流估计候选；任何缩小推理网格的优化均需单独复核画质与耗时。未达标的分辨率组合保留原帧播放，并记录明确原因。

功耗比较使用同一素材、输出帧率、画质档、显示设置与电源状态，并同时记录温度/热状态。能获取实际能量数据时按相同播放时长比较；不能测量时不以 CPU/GPU 占用替代瓦数，也不声称更省电。NPU 路线未优于 GPU 时保留真实结论，默认选择经过完整播放验证的方案。

### C. 播放回归

验证本地文件和受控 HTTP 流、开始/停止、连续换片、反复定位、暂停恢复、片尾、音轨/字幕切换、窗口/全屏及补帧关闭后的基线。验证 23.976/24/25/29.97/30 fps 时间关系，以及 HDR、变帧率和高帧率的跳过行为。用插帧计数和输出帧内容确认产生了中间帧，不能只看 `estimated-vf-fps`。

单元测试覆盖资格判定、滤镜所有权、错误回退和代次失效；插件集成测试覆盖真实模型、帧时长和参考图像。接入完成后运行既有 CTest 套件及 Mac 原生窗口测试。测量与开发使用独立配置和构建目录，不覆盖用户正在运行的应用。

### D. 安装包

应用移至含空格/中文的路径后仍可加载模型和内部依赖。清除开发环境变量、使用空白配置目录、禁用外部模型下载后，完成真实补帧播放。检查动态库实际加载路径、包内依赖闭包、签名及许可证。

Core ML 编译产物随包提供，系统生成的缓存和 VapourSynth 注册写到可写的应用数据目录，不能写入已签名的应用。迁移安装位置后能够重建路径相关缓存；安装包测试不能借用开发机现有 Homebrew 或 Python 注册信息。

### 决策规则

必须先完成模型正确性和 1080p 实时可行性验证，再做默认后端选择和产品集成。若只有 GPU 路线达标，明确交付 GPU 模式及 ANE 的验证结论；若所有路线均不达标，保留研究结果并报告阻碍，不发布一个会卡顿的“实时补帧”版本。

## 11. 交付顺序

1. 审阅本文并形成实现计划。
