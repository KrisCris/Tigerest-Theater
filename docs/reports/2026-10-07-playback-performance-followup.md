# 2.4.3 试用修订：RIFE 调度、弹幕匹配和播放反馈

本轮仍为试用候选，不创建正式标签或 Release。日常安装目录和设置不变。

## RIFE 性能定位

用户提供的 SVP 对照使用 RTX 4090、标准 RIFE 4.25、TensorRT、4 个 GPU 流。客户端实际加载的是标准 4.25、implementation 2、FP16 输入输出、静态尺寸引擎；本轮没有改成 lite、降低分辨率或把源视频降为 8 位。

首轮确认了两个独立瓶颈（后续真实片源的窗口呈现复查见文末）：

1. 最末端的统计 Monitor 使用 `fmFrameState`，串行化了上游请求。改为 `fmParallel`，并使统计支持乱序完成、去重及 seek epoch 隔离。并行回调测试实际从 1 提升至 2；百万帧乱序计数测试仍精确，测得私有内存增量为 0。
2. 修复并行后，当前 Windows gpu-next / D3D11 呈现链路使用 `display-resample` 仍持续丢帧。TensorRT 图挂载期间临时采用 `display-vdrop`；停止、失败、旁路和结束时恢复最近的用户偏好。显式选择其他同步模式时尊重该选择。CoreML 不应用此策略，结束回调不做同步 mpv 调用。

### 纯滤镜 A/B

同一 RTX 4090、标准 RIFE 4.25、1080p 10 位、24000/1001→60000/1001、2.5×。每组预热 3 秒、采样 10 秒；素材为合成测试帧，不代表所有真实片源。

| Monitor / 并发 | 吞吐 fps | 请求等待 P95 ms |
| --- | ---: | ---: |
| 不含 Monitor，2 流、prefetch 4 | 128.80 | 11.29 |
| 旧 Monitor，2 流、prefetch 4 | 64.53 | 29.00 |
| 并行 Monitor，2 流、prefetch 4 | 127.49 | 11.37 |
| 并行 Monitor，2 流、prefetch 2 | 109.69 | 13.46 |
| 并行 Monitor，4 流、prefetch 4 | 125.49 | 12.50 |

4 流没有优于 2 流，因此没有盲目增加 GPU 流数量。等待时间是整段滤镜请求耗时，不宣称等于单次 TensorRT kernel 时间。

### 首轮独立 Player 呈现 A/B（合成素材）

真实 Qt Player / MpvVideoItem，标准 RIFE 4.25，1080p HEVC 10 位 23.976→59.94 fps，3840×2160 呈现区域、240 Hz 显示器、默认受管画质配置。使用 90 秒连续合成素材，未冒充用户的《乱马》片源。统计排除启动、截图暂停和恢复预热。

| 条件 | 采样时长 | 新增显示丢帧 | 最大采样音画偏差 |
| --- | ---: | ---: | ---: |
| 旧 Monitor + display-resample | 30.01 s | 1782 | 791.94 ms |
| 并行 Monitor + display-resample | 30.01 s | 546 | 85.50 ms |
| 并行 Monitor + audio | 30.01 s | 0 | 0.011 ms |
| 并行 Monitor + display-vdrop | 30.01 s | 0 | 10.98 ms |
| 首轮自动策略，用户设置保持 display-resample | 60.01 s | 0 | 18.74 ms |

该轮 60 秒样本视频时间推进 60.00995 秒，vfFps 为 59.94006，解码新增丢帧为 0，无性能警告。启动基线已有 13 个显示丢帧，不能宣称启动至退出全过程零丢帧。

另行运行 45 秒暂停/拖动检查：暂停时视频位置稳定、向前拖动 10 秒后 epoch 更新并恢复补帧，最终仍为 display-vdrop、59.94 fps，无性能警告。seek 会重置 mpv 丢帧计数，故不以“最终减初始”的负数作为该组丢帧结论。

这些结果验证了当前机器和测试规格下的修复，不替代用户实际影片、其他显示器、驱动及更长时段的验收。

实现依据：[VapourSynth FilterMode](https://www.vapoursynth.com/doc/api/vapoursynth4.h.html#enum-vsfiltermode)、[mpv video-sync](https://mpv.io/manual/stable/#options-video-sync)。display-vdrop 仍使用显示时钟，通过丢弃或重复帧处理漂移；不对音频重采样。

## 用户反馈后的真实片源复查

用户仍报告大量输出掉帧，说明前述合成素材和独立 Player 验证不足以覆盖正式窗口。取得用户暂停播放的确认后，使用截图中《二十世纪电气目录》S1E03 的本地同一文件，1080p H.264 8 位、23.976→59.94 fps、标准 RIFE 4.25，保留默认画质和原片内嵌画面字幕；读取真实弹幕并解析出 2640 条，采样 1245 秒附近的密集区段。没有降模型、降低视频分辨率或减少弹幕条数。

第三个瓶颈是全屏呈现：旧的 `WS_BORDER` 兼容处理本来只针对 OpenGL，却也应用到了已改用 D3D11 的 Qt 场景。保持媒体、滤镜、弹幕相同，仅改变测试窗口进入全屏的方式即可复现差异。

| 实际场景 | 稳态时长 | 新增输出丢帧 | 最后估算显示刷新率 |
| --- | ---: | ---: | ---: |
| 独立 Player，强制合成边框全屏 | 30 s | 333 | 141.71 Hz |
| 独立 Player，不强制边框全屏 | 30 s | 0 | 240.004 Hz |
| 修正后的完整客户端，3840×2160 全屏、网页保留 | 60 s | 0 | 240.001 Hz |

缩小视频区域使 `display-names` 只剩一块显示器后仍有大量掉帧，因此没有把跨屏认定为主因，也没有用裁剪画面来掩盖问题。修正只在 OpenGL 场景保留边框兼容处理；Windows 窗口测试分别覆盖 D3D11 和 OpenGL、普通/最大化窗口起始状态、三次全屏往返、句柄保持及退出样式恢复。修改前两个原生 D3D11 用例失败，修改后 2/2 CTest 目标通过。

完整客户端的首轮测试脚本在加载后过早请求全屏，被随后的窗口状态回调切回窗口模式；这些样本实际为 1920×1080，只用于窗口模式分析，不能算作全屏结果。修订脚本在进入全屏后强制核验 mpv 的 3840×2160 输出尺寸再采样。旧 `without-danmaku.json` 实际仍加载了相邻 XML，同样没有当成无弹幕对照；测试入口现在明确禁用未请求的弹幕插件。

窗口模式还存在 DWM 呈现节奏问题：保留弹幕的 `display-vdrop` 样本 60 秒新增 657 次输出丢帧；真正关闭弹幕后 30 秒仍新增 319 次，说明不是弹幕条数或 RIFE 计算能力导致。无弹幕、改用音频时钟的对照 30 秒新增丢帧为 0。单独改用旧式 bitblt 或 Vulkan 不能消除窗口模式掉帧，不进入交付配置。

随后试验了窗口模式 `audio`、全屏 `display-vdrop` 的分支策略，配合原生所有权标记阻止弹幕脚本抢回时钟。窗口模式的完整客户端实测 60.875 秒，视频推进 60.894 秒，59.94006 fps，显示及解码新增丢帧均为 0；mpv 每秒采样 A/V 差的绝对最大值为 0.010 毫秒。这不是实际扬声器和屏幕物理延迟测量。

全屏更长复测推翻了“保留显示时钟已足够稳定”的判断：三组分别为 60.25 秒新增 56 次、约 60 秒新增 2 次、120.54 秒新增 110 次输出丢帧。异常呈短时集中分布，同时估计呈现刷新率下降，恢复后约 240 Hz；当前证据不能进一步断言由哪项系统活动触发。所有样本保留，没有只挑选零丢帧结果。模型始终为标准 4.25、2.5×，视频推进与采样时长一致。

最终策略因此改为：当原偏好为 `display-resample` 时，Windows TensorRT 补帧在窗口和全屏统一临时使用 `audio`，退出恢复偏好；明确选择其他同步模式时尊重选择。RIFE 的所有权标记阻止弹幕脚本竞争该设置。代价是补帧期间弹幕也随视频约 60 fps 更新，不再强制 240 Hz OSD；模型、倍率、视频分辨率、字幕和画质配置不变。Lua 回归验证所有权、恢复和实际动画更新频次。

独立代码审查补出了属性通知合并和异步写入乱序的风险。实现使用带请求编号的完成回执串联所有权标记、同步模式和恢复操作，并异步读回核实实际值，不再把“提交成功”当成“设置已生效”。红测复现了双请求并发提交、外部接管后被格式轮询重新抢回，以及恢复失败提前释放标记的问题。完整测试又抓出 startup 异步回退接口的兼容回归，已恢复原回退行为，使用独立能力标记判断真实完成回执是否可用。

补齐首次编译挂载、恢复失败后重试、释放重试期间新设置保留、停止、下一条目和过期回复的覆盖后，生命周期 / runtime manager / controller / Windows control / poll access 5/5 通过；改为统一 audio 后再次 5/5 通过（2.08 秒）。冷编译协调器测试使用 fixture，不能等同于实际重新编译模型；本轮真实播放使用已经验证的引擎缓存。END_FILE 回调保持非阻塞。
