# 120 帧与 700 ms 转场（2026-10-23 验收）

工作树 `claude/transition-no-waits`（基于 2.9.4 / 71528ef，提交 161bc42，随 2.9.4 发布），构建目录 `D:\CodexDeps\TigerestTheater\build-transition`。所有测量都用隔离配置，不碰已安装的播放器和它的设置；服务器上的用户与媒体库设置没有改动。

## 七项要求

| # | 要求 | 结果 |
|---|---|---|
| 1 | 动画保底 120 帧 | **大部分时间做到，但没有做到"每一帧都 ≤ 8.3 ms"**。不录屏、着色器缓存已预热时，每组三次转场平均 145–168 帧，p95 帧间隔 9.4–16.4 ms；每次转场仍有 0–7 帧（多数 2–5 帧）超过 17.7 ms，最长 31–51 ms。2.9.1 用录屏同法测，最长帧同样是 21–42 ms。 |
| 2 | 按下到完成 ≤ 700 ms | 目标页面按时出现时，计划落地 600–700 ms，录屏测得 600–675 ms。**例外**：返回一面本次从未显示过的海报墙时，服务器要 540–780 ms 才给出目标卡片，只能转入"晚到兜底"或最短飞行，在约 790–940 ms 结束（见"已知限制"）。 |
| 3 | 修复进详情页闪白 | 已修。逐帧检查两台服务器的六种转场，没有闪白。 |
| 4 | 点击立刻触发 | 松开鼠标即起飞（按你的选择）。录屏逐帧看，转场第一帧里海报就开始抬起。这一轮另修了起飞时卡片位置先空一到两帧的问题（见下）。 |
| 5 | 不大幅改变视觉 | 飞行、模糊遮罩、揭开的样式不变。改的是时间：海报不再原地悬停等页面，第一次进详情页也直接飞向落点。 |
| 6 | 运动以 120 帧为标准 | 网页部分默认跟随屏幕刷新率（这台 240 Hz 屏上不封顶）。可选的 120 帧上限 `TIGEREST_WEBENGINE_MAX_FPS=120` 实测并不减少长帧（见下表），所以默认不开。Qt Quick 部分（播放界面等）仍跟随屏幕刷新率。 |
| 7 | 按同样方式验收 | 已用真实 Emby 4.10 和 Jellyfin 10.11 录屏验收，逐帧图和对比视频在 `../验收-2.9.1vs新版/`。 |

## 改动

`native/homeTransitions.js`（转场引擎）

- 飞行海报改成一组嵌套图层：外层平移、内层缩放，全部是合成器动画。中途要修正落点时，新开一层从零叠加，不重启正在跑的动画，海报不会跳。
- 落点按优先级取：上次记住的落点（按窗口尺寸保存，最多 48 条）、离开时的卡片位置、按服务器布局预先算好的位置，都没有时才原地抬起，等目标出现再飞。
- 700 ms 截止：落点未知时，最后一段飞行按截止时间压缩，最短 120 ms。目标在 580 ms 之后才出现时不再飞行，海报原地淡出，页面在下面揭开（"晚到兜底"）。
- 返回海报墙时，揭开前等屏幕上的卡片图加载完；等待有上限，必须保证最短的揭开过程仍和落地同时结束。
- Jellyfin 卡片下面的深色占位框和 blurhash 画布随海报一起隐藏，免得透过模糊层露出来。
- 落地时详情页的海报图还没加载完的话，飞行海报留在上面，图到了再淡出（最多 5 秒；滚动、缩放窗口或换页时立即交还）。
- **本轮新修**：被点的卡片改为飞行海报画出来之后（两帧后）再隐藏。原来在同一帧隐藏，飞行图层要晚一两帧才上屏，中间卡片位置会空一两帧；冷启动的第一次点击最长空了约 160 ms。iPad 的 DOM 场景路径仍立即隐藏。

`native/homeMotion.js`（首页、海报墙与详情页的衔接）

- 预先写好详情页落点。Emby 和 Jellyfin 的详情页布局是固定的，按两台真实服务器在多种窗口尺寸下实测的布局规则计算（不是写死像素）：
  - Emby：左侧抽屉 238 px，页边距在 1440 px 宽处变宽；剧集、电影、单集用竖版海报，季和合集更窄，横图卡片更宽。
  - Jellyfin：窗口宽于 1000 px 时海报宽为窗口的 1/4，窗口较矮时下移到页头下方。
  - 没实测过的布局（竖屏、过窄、过宽）不猜，走原地抬起。实测落点误差：Emby 0.0 px，Jellyfin 0.4 px。
- 海报墙预取：进入服务器后，在首页空闲时读取每面已学到的海报墙的轻量索引（ID 和排序键）。从详情页返回时，一按下就把海报墙会发的查询提前发出。
- Emby 虚拟列表：返回时直接加载屏幕上需要的分块（一屏横跨 2–3 块，每块 50 张）。不再等滚动条约 170 ms 的防抖后才请求，揭开时就不会出现空行。

QtWebEngine 和客户端

- 两个新补丁：`begin-frame-cap`（可选帧率上限）和 `shader-disk-cache`（GPU 着色器磁盘缓存，重启后第一次转场不用现编译）。说明见 `dev/windows/qtwebengine/README.md`。
- `src/main.cpp`：着色器缓存默认放在当前配置的 `GPUCache`。
- `src/utils/win/ThreadSampler.*`：两个默认关闭的诊断开关，`TIGEREST_FRAME_TIMES`（原生换帧时间）和 `TIGEREST_THREAD_SAMPLES`（线程采样），见 `dev/windows/TESTING.md`。

## 测量

### 方法

- **帧间隔：不录屏，看原生换帧时间。** 设 `TIGEREST_FRAME_TIMES`，主窗口每次 `frameSwapped` 记一个时间戳，统计从点击到转场结束之间的间隔。屏幕 240 Hz：超过 9.5 ms 算低于 120 帧，超过 17.7 ms 算掉了一帧。早先用的 Qt 渲染循环调试日志本身会拖出卡顿，已弃用。
- **着色器缓存：预热。** 模拟安装版重启后的状态。测试用的全新配置副本缓存是空的，第一次转场会多一次约 65 ms 的着色器编译卡顿；安装版只在首次安装、升级 QtWebEngine 或更换显卡驱动后遇到一次。
- **画面：录屏。** DXGI 桌面复制 240 Hz，用来逐帧看画面有没有突变；它本身会让网页合成掉到 120–190 帧，所以帧间隔不以录屏为准。2.9.1 没有换帧计时，和 2.9.1 的对比只能都用录屏。
- **页面计时会晚于画面。** "落地 ms"取自页面主线程，主线程忙时比合成器上的动画晚几十毫秒。同理，页面内的"海报开始移动"读数（44–115 ms）不能代表画面；录屏逐帧看，海报在转场第一帧就开始动。

## 逐帧检查结论

- **首页→详情**：第一次就飞向预设落点，落地后和真实海报重合，没有回弹、没有闪白。落地后剧集缩略图或 logo 晚几十毫秒出现，这是详情页自己的内容在加载（2.9.1 同样如此）。
- **海报墙→详情**：卡片留在原位，海报盖上去后再隐藏，飞行连续。
- **详情→海报墙**：揭开时屏幕上的卡片都已有图（之前 Emby 揭开时下面几排是空灰占位，约 100 ms 后一起冒出来）。海报落回自己的格子。
- **起飞首帧**：修复前，预热缓存下卡片位置空 1 帧，冷启动空 2 帧到约 160 ms；修复后两台服务器、各三轮、三种转场里都不再出现。

## 已知限制

1. **返回一面本次从未显示过、图片也不在磁盘缓存里的海报墙**（例如从首页点进详情页后第一次返回）：
   - Emby 生成这个页面要约 690–780 ms，转入晚到兜底，约 790–940 ms 结束；揭开时卡片已有数据，但图片要再过约 80 ms 才补齐。
   - Jellyfin 约 800–850 ms 结束；揭开时卡片还是 blurhash 模糊占位，真图到 900–1000 ms 才出来。

   看过的墙，图片会留在安装版的磁盘 HTTP 缓存里，以后不会再这样。彻底解决需要提前下载这面墙首屏的图片；但图片地址里的尺寸参数由服务器网页按窗口宽度算出，要从显示过的海报墙上学到规律才能拼对，可以作为下一步。
2. **第一次返回某个条目**（还没记住它在墙上的落点）：海报要在暗场里悬停约 250 ms，等墙给出目标位置再飞（2.9.1 约 900 ms）。返回一次之后就会记住。
3. **每次转场仍有 0–7 帧超过 17.7 ms。** 线程采样显示卡顿时 GPU 线程在光栅化新页面（文字、模糊、图片），页面主线程在排版，没有单一的大头。
4. **Jellyfin 预取只覆盖海报墙的第一页**（前 100 项）。排在后面的条目第一次返回时走原地抬起。
5. **冷着色器缓存**：首次安装或升级后的第一次转场，有一次约 65 ms 的着色器编译卡顿。
